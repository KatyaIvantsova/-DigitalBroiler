# S2-08. Спецификация движка правил

Статус: **черновик для утверждения разработкой** (issue #26). Реализация — S3-03…S3-07 (микроклимат, освещение, потеря данных), S4-05 (корм, вода, стадо).

## 1. Задача

Сравнивать показания датчиков и данные учёта с нормой для **возраста партии и кросса**, создавать инцидент, когда отклонение держится дольше заданного времени, не плодить дубли и закрывать инцидент, когда показатель вернулся в норму. Сейчас (до S3) правила есть только для освещения, с константами 25–40 лк.

## 2. Входные данные

| Источник | Что берём |
|----------|-----------|
| Активная партия птичника | кросс, дата посадки → возраст в днях по часовому поясу площадки |
| Справочник норм (S3-01) | `min`, `target`, `max` по показателю, кроссу и возрасту, активная версия |
| Датчики птичника | привязка к птичнику и зоне (S2-07), тип |
| InfluxDB | показания датчика за окно правила |
| Ежедневный учёт | падёж, выбраковка, корм, вода за сутки (правила S4-05) |

Нет активной партии — правила по возрасту для птичника не проверяются (санобработка, пустой птичник); работает только правило «нет данных», если датчик активен.

## 3. Правило

| Поле | Пример | Смысл |
|------|--------|-------|
| `code` | `MICROCLIMATE_TEMPERATURE` | уникальный код, пишется в `incidents.rule_code` |
| `metric` | `TEMPERATURE` | показатель справочника норм |
| `sensor_type` | `TEMPERATURE` | какие датчики проверять (`null` для правил по учёту) |
| `incident_type` | `MICROCLIMATE` | тип инцидента |
| `warn_minutes` | 30 | сколько минут подряд значение должно быть вне `[min, max]` для предупреждения |
| `critical_delta` | 2.0 | насколько выйти за границу нормы для критичного уровня (в единицах показателя); `null` — без критичного уровня |
| `critical_minutes` | 15 | сколько минут держится критичное отклонение |
| `clear_minutes` | 15 | сколько минут значение в норме, чтобы закрыть инцидент |
| `enabled` | true | правило включено |

Пороги по умолчанию — из [норм S1-03](../sprint1/03-norms.md): температура ±1 °C 30 мин / ±2 °C 15 мин, влажность вне диапазона 60 мин / ±10 п. п. 30 мин, CO2 > 2500 ppm 30 мин / > 3000 ppm 15 мин, NH3 > 10 ppm 30 мин / > 20 ppm 15 мин, освещённость вне диапазона 30 мин.

## 4. Алгоритм (на каждый датчик, раз в минуту)

1. Найти активную партию птичника датчика, возраст `d`, кросс `b`. Взять норму `N(metric, b, d)`; нет нормы — пропустить.
2. Взять показания датчика за последние `max(warn, critical, clear)` минут.
3. **Уровень**:
   - `CRITICAL`, если все показания за последние `critical_minutes` ниже `min − critical_delta` или выше `max + critical_delta` (и их не меньше двух);
   - `WARNING`, если все показания за последние `warn_minutes` вне `[min, max]`;
   - `NORMAL`, если все показания за последние `clear_minutes` внутри `[min, max]`;
   - иначе состояние не меняется (переходная зона — защищает от дребезга).
4. **Дедупликация**: ключ `rule_code + sensor`. Если по ключу есть незакрытый инцидент (`OPEN`, `IN_PROGRESS`):
   - уровень вырос (WARNING → CRITICAL) — поднять приоритет, записать в историю;
   - уровень тот же — ничего не делать;
   - нового инцидента не создаётся.
5. **Создание**: открытого инцидента нет, уровень WARNING или CRITICAL → инцидент с `source = SYSTEM`, `rule_code`, `house_id`, `zone_id`, `flock_id`, `sensor_id`, приоритет `HIGH` (warning) или `CRITICAL`, описание «Температура 31,4 °C при норме 26,3 ± 1,0 °C (день 8, Ross 308) дольше 30 мин».
6. **Автозакрытие**: уровень NORMAL, а открытый инцидент правила ещё `OPEN` (никто не взял) — статус `RESOLVED`, комментарий «Показатель вернулся в норму», запись в историю. Если инцидент `IN_PROGRESS`, его не закрываем — им занимается человек; добавляется только запись в историю «показатель в норме с HH:MM».

## 5. Потеря данных (S3-07)

Активный датчик, привязанный к птичнику, не присылал показаний дольше `NO_DATA` минут (по умолчанию 30) → инцидент `NO_DATA`, приоритет `HIGH`, дедупликация по датчику, автозакрытие при первом новом показании.

## 6. Правила по учёту (S4-05)

Проверяются раз в сутки после ввода учёта и при каждой правке учёта:

| Код | Условие | Приоритет |
|-----|---------|-----------|
| `FLOCK_MORTALITY_DAILY` | падёж + выбраковка за сутки выше нормы дня (S2-11) | HIGH, ×2 нормы — CRITICAL |
| `FEED_DROP` | расход корма за сутки упал > 10 % к предыдущим суткам | HIGH, > 20 % — CRITICAL |
| `WATER_DROP` | расход воды упал > 10 % к предыдущим суткам | HIGH, > 20 % — CRITICAL |

Ключ дедупликации — `rule_code + flock + дата`.

## 7. Статус категорий дашборда

Категория (микроклимат, освещение, производство, ресурсы, стадо) красная, если по её правилам есть открытый CRITICAL; жёлтая — есть открытый HIGH/MEDIUM; иначе зелёная. Это заменяет захардкоженные статусы (S4-03).

## 8. Нефункциональные требования

- Цикл проверки — 1 минута, 500 датчиков (10 птичников × 50) укладываются в цикл с запасом: один запрос в Influx на датчик или пакетный запрос по птичнику.
- Правило, норма и порог — данные, а не код: изменение нормы применяется со следующего цикла без перезапуска.
- Каждый автоматический переход (создание, повышение, автозакрытие) пишется в историю инцидента и журнал действий от имени «Система».

## 9. Вопросы к разработке и PO

1. Проверка по каждому датчику или по среднему по зоне (сейчас — по датчику, дубли по зоне отсекаются при отображении).
2. Нужно ли подавлять правила микроклимата в первые сутки после посадки (прогрев птичника).
