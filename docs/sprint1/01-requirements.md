# S1-01. Требования к Модулю 1 «Контроль и мониторинг»

Статус: **черновик для согласования с PO и командой** (issue #1).

## 1. Цель модуля

Дать технологу и руководителю птицефабрики единый ситуационный центр: данные датчиков и учёта по каждой партии, сравнение с нормой кросса по возрасту, инциденты при отклонениях и KPI партии. Решения принимает человек; автоматическое управление оборудованием — Модуль 2.

## 2. Границы

**Входит в Модуль 1**

| Блок | Состав |
|------|--------|
| Структура производства | площадка → птичник → зона; партия с посадкой, кроссом, поголовьем, закрытием |
| Сбор данных | телеметрия (HTTP, позже MQTT): температура, влажность, CO2, аммиак, освещённость, расход корма и воды; ручной ввод и импорт учёта (падёж, выбраковка, взвешивания, корм) |
| Нормы | справочник норм по возрасту и кроссу (Ross 308, Cobb 500) с версионированием |
| Правила | проверка показаний по нормам с учётом длительности отклонения и приоритета, дедупликация и автозакрытие |
| Инциденты и задачи | уведомление → инцидент (SLA реакции 30 мин) → задачи; вложения; история |
| KPI партии | FCR, сохранность, среднесуточный привес, длительность цикла, EPEF, план-факт |
| Ситуационный центр | главная по партии, экран партии, карта птичника с зонами, сводка по площадке, отчёт PDF |
| Оповещения | Telegram по приоритету и подписке на птичник, эскалация по SLA |
| Доступ | вход, роли, назначение на птичники, журнал действий |
| Эксплуатация | CI, прод-сборка, бэкапы, мониторинг платформы, развёртывание on-prem и в облаке |

**Не входит** (Модуль 2 и 3): управление оборудованием через АСУ ТП, видеоаналитика (поведение, вес по видео), ИИ-прогнозы и рекомендации, цифровой двойник, мобильное приложение.

## 3. Роли пользователей

| Роль (`access_role`) | Кто это | Основные действия |
|------|---------|-------------------|
| OPERATOR — оператор | старший смены, птичница | ввод падежа, взвешиваний, корма; видит свои птичники; берёт инциденты в работу |
| TECHNOLOGIST — технолог (зоотехник) | отвечает за технологию выращивания | всё, что оператор, по всем птичникам площадки; правит нормы; закрывает инциденты |
| VETERINARIAN — ветеринар | ветслужба | инциденты по состоянию стада и падежу; отметки о лечении и выбраковке |
| MANAGER — руководитель | директор по производству или качеству | просмотр всего, KPI, отчёты, сводка; без правки справочников |
| ADMIN — администратор | ИТ | пользователи, роли, датчики, интеграции |

Матрица прав по действиям — задача S2-04. В спринте 1 любая роль даёт полный доступ к API, проверяется только вход.

## 4. Функциональные требования (верхний уровень)

1. Пользователь входит по логину и паролю. Без входа API отвечает 401 (реализовано в S1-09).
2. Партия создаётся с датой посадки, кроссом, поголовьем и птичником. Возраст в днях считается автоматически.
3. Каждый день по партии вводятся падёж, выбраковка, взвешивание, корм и вода. Правки сохраняются в истории.
4. Показания датчиков сравниваются с нормой для возраста партии и кросса. Отклонение дольше заданного времени создаёт инцидент нужного приоритета, повторы не плодятся, при возврате в норму инцидент закрывается.
5. Молчание датчика дольше N минут — отдельный инцидент «нет данных».
6. KPI партии считаются из учёта и совпадают с эталонными расчётами QA (S1-04, S3-08).
7. Главная показывает статус по категориям (освещение, микроклимат, производство, ресурсы, стадо) из движка правил, без захардкоженных значений.
8. Инцидент уходит в Telegram подписчикам птичника; при нарушении SLA срабатывает эскалация.
9. По закрытой партии формируется отчёт PDF: KPI, инциденты, отклонения.

## 5. Нефункциональные требования

| Требование | Значение |
|------------|----------|
| Нагрузка | 10 птичников × 50 датчиков, интервал 1 мин (S6-03) |
| Задержка | показание видно в интерфейсе не позже 1 мин после приёма |
| Доступность платформы | падение backend видно за 5 мин (S5-08) |
| Хранение | телеметрия не менее 2 циклов (≈ 120 дней) в детализации, дальше агрегаты |
| Безопасность | секреты только из окружения; наружу только 80/443; пароли в bcrypt; роли проверяются на backend |
| Развёртывание | on-prem или облако по одной инструкции (S6-05) |
| Язык интерфейса | русский |

## 6. Критерии приёмки модуля (DoD Модуля 1)

Модуль принят, когда на пилотной площадке (или стенде с реальными датчиками) выполнены все пункты:

- [ ] Полная партия прожита в системе от посадки до закрытия (реальная или симулятор 42 дня).
- [ ] Данные пилота поступают автоматически: датчики и импорт учёта.
- [ ] Нормы Ross 308 и Cobb 500 загружены, отклонения по микроклимату, освещению, корму, воде и стаду создают инциденты.
- [ ] Ложных срабатываний меньше согласованного порога (порог фиксируется на S5-13).
- [ ] KPI партии совпадают с эталонами QA, базовая линия пилота зафиксирована.
- [ ] Оповещения и эскалация работают по согласованной матрице.
- [ ] Роли и журнал действий проверены, чек-лист ИБ пройден.
- [ ] Нет открытых блокирующих и критичных дефектов.
- [ ] Есть руководство пользователя по ролям и инструкция развёртывания; чистый сервер поднимается по инструкции.
- [ ] Подписан протокол приёмки (S6-07).

## 7. Открытые вопросы к PO

1. Порог ложных срабатываний для приёмки (например, не больше 10% инцидентов, закрытых как «ложное»).
2. Какие учётные системы у пилота (1С, Excel, своя система) — влияет на S4-07.
3. Нужен ли вход через корпоративный каталог (LDAP/Keycloak) уже в Модуле 1 или хватит локальных пользователей.
4. Срок хранения телеметрии и требования заказчика к размещению данных.
